Nursia · Growth engineering · Sprint PRD

Every paid click loses its name at the door.

Meta Pixel is installed and firing. Google Ads is configured and bidding. Neither can currently attribute a signup, because the handoff from nursia.io to app.nursia.io is a bare server redirect that discards the query string — and with it every click identifier the ad platforms rely on. This document specifies the fix, the Conversions API build on top of it, and the activation and high-intent measurement that has nowhere to land until both are done.

Finding 01 · Ship before anything else

The redirect throws away the query string.

src/app/(funnel)/signup/page.tsx is four lines: redirect("https://app.nursia.io"). Next's redirect() issues a 307 to exactly that URL. Nothing on the incoming URL survives it.

CtaLink does careful work to carry utm_source, utm_medium, utm_campaign, utm_content, utm_term, gclid and fbclid from the ad click through to the signup link. All of it is discarded one hop later.

ad click · gclid + fbclid→ /lp/meta · CtaLink collects→ /signup?utm_source=…&fbclid=…→ 307 · params dropped→ app.nursia.io · anonymous

Three consequences, all live right now. Google Ads receives no gclid at the point of signup, so the campaign's primary conversion cannot be attributed to a click. Meta sets no _fbc cookie on the app domain, so pixel and CAPI events arrive without click attribution and delivery optimisation degrades toward broad targeting. GA4 gets no linker parameter, so the app is counted as a separate session referred by your own marketing site — which is also why organic and paid look closer than they are.

Finding 02 · Ship before anything else

The conversion the campaign bids toward can no longer fire.

signedUp() in src/lib/analytics.ts fires three things: the GA4 sign_up event, the Google Ads primary conversion (AW-18411895345/SfHmCJ…), and the Meta standard event CompleteRegistration. It is called from exactly one place — src/components/SignupForm.tsx.

SignupForm is rendered by src/app/(funnel)/signup/page.tsx, which is now a redirect stub with its original body commented out. The component never mounts on nursia.io. All three events are unreachable code.

Smart Bidding is currently optimising against a conversion that records zero. The same is true of loggedIn(), examStarted() and examCompleted(), whose call sites live in components behind the same stubs.

Why activation is an event and not a cohort

Both GA4 and PostHog can express "performed question_answered at least five times" as an audience or behavioural cohort. Both re-evaluate it on a schedule, neither gives it a timestamp, and neither can sit cleanly as a step inside a funnel exploration. A milestone event fired once, at the moment the counter crosses five, is a real funnel step, carries the channel properties of the person who earned it, and can be sent to Meta as a conversion. The counter itself is cheap: the attempt queue in src/lib/attempts.ts already persists every answer to localStorage, and src/lib/experiment.ts already holds a stable anonymous id to hang a fired-once flag on.

W1 · Reference implementation

What the redirect stubs should look like

Four files, one shape. The stub keeps its job — send people to the app — and stops throwing away the reason they came. 

// src/app/(funnel)/signup/page.tsx
import { redirect } from "next/navigation";

const APP = "https://app.nursia.io";

/* Everything the ad platforms and our own funnel need on the far side.
   A bare redirect() drops all of it, which is how a campaign ends up
   bidding toward a conversion it can no longer attribute. */
const CARRY = [
  "utm_source", "utm_medium", "utm_campaign", "utm_content", "utm_term",
  "gclid", "fbclid", "src", "guide", "resource", "experiment", "variant",
] as const;

export default async function SignupPage({
  searchParams,
}: {
  searchParams: Promise<Record<string, string | string[] | undefined>>;
}) {
  const from = await searchParams;
  const out = new URLSearchParams();
  for (const key of CARRY) {
    const v = from[key];
    const one = Array.isArray(v) ? v[0] : v;
    if (one) out.set(key, one);
  }
  const qs = out.toString();
  redirect(qs ? `${APP}/signup?${qs}` : `${APP}/signup`);
}

Two things this does not fix on its own

The cookie boundary. Meta's _fbp and _fbc are first-party cookies written by fbevents.js on the host that set them. A cookie set on nursia.io is not readable by app.nursia.io unless its domain attribute is .nursia.io. Forwarding fbclid lets the app mint its own _fbc, which is the simpler path and the one this PRD recommends; setting the cookie at apex scope is the alternative and needs both hosts to agree.

GA4 session continuity. Forwarded UTMs will make the app's traffic look right, but GA4 still starts a new session unless app.nursia.io is added to the cross-domain list in Admin → Data streams → Configure tag settings. Do that before reading any cross-domain funnel, or the numbers will be confidently wrong.

W3 · Decision

Where the server-side events should come from

You asked for the call to be made here rather than left open. It is made below, with the reasoning.

OptionCostControl of event_idOps burdenVerdict

Meta Conversions API Gateway
Meta-hosted on your cloud		 Cloud instance, roughly $40–90/mo Partial — the gateway derives it Low, but opaque when wrong Reject at this stage
Partner integration
Segment, Stape or similar		 Per-event pricing, scales badly Good Lowest Revisit past ~1M events/mo

Recommendation — own the route

At your current volume the Gateway's monthly cost buys convenience you do not need, and it takes deduplication partly out of your hands at exactly the moment deduplication is the hard part. A route handler on the Railway deploy you already run costs nothing extra, keeps the dedup contract in code that sits next to the pixel it is deduplicating against, and matches how src/lib/analytics.ts already centralises every event in one place. Revisit only if event volume or retry handling becomes a real operational load.

The deduplication contract

Meta collapses a browser event and a server event into one when event_name matches and event_id matches. Generate the id once on the client, pass it to fbq as eventID, and send the same string in the CAPI payload's event_id. Getting this wrong double-counts every conversion, which is worse than the under-counting it was meant to fix — so the acceptance test below checks the dedup rate in Events Manager, not merely that events arrive.

On channel properties

Do not hand-roll a channel classifier. GA4's Default Channel Group already separates Organic Search, Paid Search and Paid Social, and it is the dimension the funnel should break on. The one thing it needs from you is correct tagging: GA4 classifies from utm_source and utm_medium and ignores fbclid entirely. An untagged Meta ad lands in Referral or Direct, not Paid Social. Every Meta ad URL needs utm_source=facebook (or instagram) and utm_medium=paid_social before this dashboard tells the truth.

Done means

Acceptance criteria

Attribution survives the boundary

A click on a Meta ad with fbclid present arrives at app.nursia.io with that parameter intact, and the resulting signup appears in Ads Manager attributed to the campaign — not in the modelled bucket.

The primary conversion records again

Google Ads shows a non-zero count for the signup conversion within 48 hours of NUR-03 shipping, and GA4 DebugView shows sign_up on a real signup.

Server and browser events deduplicate

Events Manager reports deduplicated pairs for Lead and CompleteRegistration rather than doubled totals, and event match quality is 6.0 or better on the server-side events.

The funnel answers the question it was built for

A single GA4 exploration shows landing → engaged → registered → activated → high intent, broken by channel, with organic, Paid Search and Paid Social each on their own line and each step's drop-off legible.
